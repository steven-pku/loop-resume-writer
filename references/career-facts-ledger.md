# 经历事实账本（career-facts ledger · schema v1）

> 双件共享 schema：loop-resume-writer 与 loop-interview-writer 各自内置本文件拷贝，版本号对齐（改动必须双仓同步并升版本）。
> 账本是全 skill 的事实地基：简历上写的、面试里说的，都只能来自这里。
> **能力边界（对外表述据此）**：账本保证的是「skill 不主动编造 + 数字强制溯源 + 简历面试口径一致」；它**不能**验证用户本人提供的数字真伪，也**不能**阻止用户离线篡改账本后再导入。对外一律说「反编造 / 可追溯 / 口径一致」，不说「防造假 / 测谎 / 背调」。

## Schema

```markdown
# Career-Facts Ledger · {候选人} · ledger-schema v1

## 经历条目 E{NN}
- 事实描述（用户给定）：
- 时间 / 组织 / 角色：
- 量化点：{描述} = {数值或〔待补数据〕}
  - 来源标注（三选一，必填）：用户提供 / 合理推算（依据：…）/ 〔待补数据〕
- 可讲的故事角度：（一条经历可有多个角度，逐条列）
- 关联目标：（JD 需求编号 / 面试高频题型）
```

## 账本纪律（不可妥协）

1. **条目只能来自用户输入**。转述允许，无中生有禁止。
2. **量化点三选一来源标注**：
   - 用户提供：原话或原始材料里有。
   - 合理推算：只能基于用户明确给出的、与该数字**直接相关**的原始数据做算术推导，写明推算式且用户可复核（如「用户说日均处理 40 单 × 22 个工作日 ≈ 880 单/月」）。**硬线：不得用团队级投入 / 行业均值 / 常识猜测 / 平台样本来补候选人个人成果**——「团队 5 人 × 6 个月 ≈ 2.5 人年」这类用团队投入反推个人贡献即非法推算；拿不准时优先标〔待补数据〕，不硬凑。
   - 〔待补数据〕：该有数字但用户没给——保留标记，进追问清单。
   - **模糊量 / 区间值**（如「涨粉几百」「大概几千」）：先追问精确值；无法精确则降为定性表述（如「带来显著涨粉」），**成稿不保留孤立的模糊数字**。模糊量不得作为合理推算的输入去推出更精确的数字。
3. **〔待补数据〕禁止在任何成稿中变成具体数字**。QA 真实性审计逐条核对。
4. **拒绝编造（拒 + 替代）**：用户要求虚构经历/岗位/数字时——
   - 明确拒绝该目标，一句话说明边界（「本 skill 只做真实经历的表达优化，不编造经历与数字」）；
   - 立即给替代动作：从账本已有条目里挖掘未被充分表达的价值（换故事角度 / 补推算依据 / 追问真实数据）。
   - 不做「念一遍免责声明然后照写」。

## 追问清单模式

缺量化数据时，生成**具体到可直接回答**的问题，而不是「请提供更多数据」：

```markdown
## 追问清单（回答后账本自动升级）
1. E02 的营销活动：上线后 30 天内转化率/GMV/获客成本相比之前变化多少？
2. E03 的流程改造：处理一单的时间从多少降到多少？覆盖多少人/单量？
3. E05 的团队规模：你直接带几个人？项目预算量级？
```

问题上限一次 5 条，按对目标 JD 的重要性排序。

## 复用约定

- 账本以独立 markdown 交付用户保存；再次使用（改投其他 JD / 跑 loop-interview-writer）直接导入。
- 面试答案中的每个事实/数字必须能在账本中定位。**账本是真相基准**：答案偏离账本 = fatal；答案与简历不一致时，先判谁偏离账本——若简历偏离账本，守真实答案并标记「需修简历」（→ loop-resume-writer）；若答案偏离账本，则答案 fatal。不为迁就一份注水简历而教人圆谎（interview 侧执行）。
