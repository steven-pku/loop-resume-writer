# Resume QA Rubric（/100）

> 打分前先跑真实性审计（账本逐条核对）；审计不过直接 fatal，不进入打分。
> 每处扣分必须引用简历原句。阈值：≥85 且无 fatal＝Pass；82-84＝Borderline（修 2 个最低维度后复查）；<82 或任一 fatal＝Revise。硬停 2 轮。
> 分数是**内部 QA 相对信号**，"Pass" 指「无已识别 fatal + 达 rubric 线」，不预测「这份简历一定能拿面试」（85 分简历在强候选池仍可能落选，冷门岗 78 分也可能够用）。

## 六维评分

### 1. JD 匹配与平台搜索命中 /25

- 23-25：映射矩阵硬需求全覆盖或已声明；技能词与 JD 原词对齐且具体（「PyTorch 实战」而非「机器学习」）；无关键词堆砌感。
- 15-22：主要需求覆盖但表述泛化；部分 JD 原词未对齐。
- <15：与目标岗位错位；关键需求未覆盖也未声明。
- 注意：命中靠**真实技能的具体化表述**，不靠埋点堆词。与经历无关的关键词＝真实性问题，转 fatal 审计。

### 2. 成就量化 /25

- 23-25：主要条目动作→结果完整，数字有来源标注；量化密度高但不硬凑。
- 15-22：有量化但关键条目仍是职责描述（「负责 X」无结果）。
- <15：通篇动作无结果。
- 无法量化的条目允许用定性结果（「上线后成为团队默认流程」），但不能全篇皆定性。
- **硬数据稀缺岗高分路径**（应届 / 转行早期 / 设计 / 学术研究 / 0-1 早期等）：缺硬数字 ≠ 低分，**不得诱导编数字**。用可验证的定性成果同样可拿 23-25——作品链接、可核实的角色边界与范围、被采用/被复用/被沿用的事实、影响的对象规模（服务 N 人/覆盖 N 个团队）、可查的产出（论文/专利/开源/获奖）。此类候选人的「23-25」标准＝成果**具体且可核实**，而非必须带数字。

### 3. 真实性风险 /15

- 13-15：全部数字带来源标注；推算依据成立；〔待补数据〕如实保留。
- 8-12：个别数字来源模糊需澄清。
- <8：出现账本外内容（即使「听起来合理」）——同时触发 fatal。

### 4. 结构与信息密度 /15

- 13-15：一页纪律达标（应届/5 年内）；倒序；当前角色权重最大；无关经历已裁剪。
- 8-12：结构对但密度失衡（老经历占比过大 / 项目罗列不分主次）。
- <8：时间线混乱或无关经历占主体。

### 5. 语言 /10

- 9-10：动词具体有力；无空话（精通/熟悉/参与/协助 滥用）；句式紧凑。
- 6-8：个别空话；动词弱（「进行了」「参与了」）。
- <6：通篇职责腔。

### 6. 筛读友好 /10

- 9-10：首屏动线顺（当前角色/公司 → 时间连续性 → 教育背景一眼可得）；版式无噪声。
- 6-8：关键信息在但动线绕。
- <6：初筛 scan 抓不到定位。
- 依据分级：眼动动线为英文语境一手研究的方向性迁移（见 evidence-notes.md），不承诺「N 秒定生死」。

## Fatal issues（一票 Revise）

1. 编造经历或数字（含〔待补数据〕被填成实数、账本外条目）
2. 全篇无任何量化结果
3. 无关经历占主体
4. 空泛技能罗列（「精通 X」背后无经历支撑）
5. 时间线断裂未处理未解释
6. JD 硬需求未覆盖且未进「无法覆盖」声明

## 修订规则要求

坏例：「提高量化程度」。
好例：「E02 条目把『负责社群运营』改为账本角度 2：『搭建 3 层社群体系，6 个月用户从 X 到 Y（数据待用户补充后填入）』」。
